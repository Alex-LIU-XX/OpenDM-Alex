## 0. 两条命令速查

两台机器各一条命令，隧道与就绪探测都封装在脚本里：

```bash
# ① 服务端（策略所在机器，本环境为 A100）
ssh A100
cd /root/workspace/opendm
bash script/robodojo_policy_server.sh setup     # 仅首次：准备代码 + 隔离 venv
nohup bash script/robodojo_policy_server.sh start </dev/null > /tmp/policy_server.log 2>&1 &
bash script/robodojo_policy_server.sh status    # server/port/gpu/staged 一览

# ② 客户端（仿真所在机器，本环境为 4090）
ssh robodojo
cd /root/workspace/Alex/robodojo
bash scripts/internal/split_policy_client.sh run --task cover_blocks --eval-num 1
```

客户端脚本会自动完成：建 SSH 隧道 → 等策略服务真正应答 → 跑 `robodojo.sh client` → 收尾关隧道。

> **要跑得快**：本文只讲「怎么用」。2 卡的最优并行配置是 **`--procs-per-gpu 2 --envs-per-proc 5`**（20 环境，实测 **9.25 步/秒**，比默认快 35 %），直接可抄的命令见 **3.5**；完整参数矩阵、四条资源红线、调参决策树见 **`评测性能分析与调参指南.md`**。

收尾与排查：

```bash
bash script/robodojo_policy_server.sh stop           # 服务端：停服务、释放显存
bash scripts/internal/split_policy_client.sh status  # 客户端：隧道/服务/策略目录 状态
bash scripts/internal/split_policy_client.sh tunnel-down
```

> **`</dev/null` 不能省**：若后台进程继承了 ssh 通道，`ssh host '... &'` 会**一直挂着不返回**（命令其实已经执行了）。加上 `</dev/null` 即可正常返回。客户端脚本内部启动隧道时也带了 `</dev/null`。

```
└───────────────────────────────────────────────────────────────────┘
```

**为什么必须走隧道**：两台都是容器实例，**只对外映射了 SSH 端口**（A100→2537，4090→5727），任意业务端口从公网不可达（实测 `120.48.62.164:7891` 为 CLOSED）。两台之间 SSH 互通（4090→A100:2537 ✅，A100→4090:5727 ✅），因此在客户端侧建 `ssh -L` 隧道即可。

**协议**：XPolicyLab 自带的 **WebSocket** 策略协议（`protocol: ws`），不是 OpenDM 的 HTTP `/v1/infer`。隧道对 ws 透明，无需额外配置。

## 3. 使用步骤

两个脚本是本链路的入口，隧道、就绪探测、依赖补齐都封装在里面：

| 脚本 | 所在仓库 | 子命令 |
| --- | --- | --- |
| `script/robodojo_policy_server.sh` | OpenDM | `setup` / `start` / `status` / `stop` |
| `scripts/internal/split_policy_client.sh` | RoboDojo | `run` / `tunnel-up` / `tunnel-down` / `status` |

### 3.1 服务端准备与启动

```bash
ssh A100
cd /root/workspace/opendm

bash script/robodojo_policy_server.sh setup    # 仅首次；幂等，可重复执行
nohup bash script/robodojo_policy_server.sh start </dev/null > /tmp/policy_server.log 2>&1 &
bash script/robodojo_policy_server.sh status
```

`setup` 做四件事（全部幂等）：

1. 从 RoboDojo 检出复制 `XPolicyLab`（**排除 `policy/Pi_05`**，它单独占 9.4 G）到 `$WORKDIR/xpl`；
2. 复制 `env_cfg`（策略适配器靠它推导动作维度，必须与客户端一致）；
3. 建**叠加式 venv** 并补装 `h5py / websockets / msgpack / msgpack-numpy` —— **不触碰共享 conda 环境**；
4. 校验关键文件与 import。

启动行为要点：

- **首次启动约 2–3 分钟**（从 CFS 读 23 GB 权重），**后续约 20–40 秒**（页缓存命中）
- ⚠️ 日志会**块缓冲**，`Loading weights` 停住不代表卡死；**以端口监听为就绪判据**
- 客户端脚本会自己等就绪，通常**不需要手动等待**

`setup` 参数：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--robodojo-repo PATH` | `/root/workspace/RoboDojo` | 提供 `XPolicyLab/` 与 `env_cfg/` 的 RoboDojo 检出 |
| `--workdir PATH` | `/root/workspace/Alex` | 代码与 venv 的落盘位置 |
| `--force` | — | 即使已暂存也重新复制代码 |

`start` 参数（均可用环境变量覆盖）：

| 参数 | 环境变量 | 默认 |
| --- | --- | --- |
| `--ckpt PATH` | `ROBODOJO_CKPT` | `/mnt/cfs/opendm/checkpoints/DM05-MEM-Robodojo-Sim` |
| `--port N` | `ROBODOJO_PORT` | `7891`（第 i 个进程监听 `N+i`） |
| `--procs K` | — | `1`。**保持 1**：每个进程都要各自加载一份权重，加载时宿主内存峰值约 **65 GB**，而容器 cgroup 上限只有 119 GB → **K≥2 会被内核 OOM 杀掉** |
| `--task NAME` | `ROBODOJO_TASK` | `cover_blocks` |
| `--bind-host HOST` | `ROBODOJO_BIND_HOST` | `127.0.0.1`（走隧道时保持回环） |
| `--gpu ID` | `ROBODOJO_GPU` | `0` |

`stop` / `status` 也接受 `--port` / `--procs`，但只用于定位与报告（内部一次 `pgrep`/`pkill` 覆盖全部进程）。

### 3.2 客户端跑推理

```bash
ssh robodojo
cd /root/workspace/Alex/robodojo
bash scripts/internal/split_policy_client.sh run --task cover_blocks --eval-num 1
```

`run` 依次做：**建隧道（含连通性前置检查）→ 等策略服务真正应答 → 跑 `robodojo.sh client` → 关隧道**。

`split_policy_client.sh` 参数（`--` 之后的参数**透传**给 `robodojo.sh client`）：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--ssh-target HOST` | `A100` | SSH 别名，或直接写 `user@host` |
| `--ssh-port N` | 取自 ssh config | SSH 端口 |
| `--ssh-key PATH` | `~/.ssh/id_ed25519` | 免密私钥 |
| `--policy-port N` | `7891` | 要桥接的远端端口 |
| `--policy-dir PATH` | `XPolicyLab/policy/OpenDM` | 仓库相对路径 |
| `--conda-env NAME` | `RoboDojo` | 仿真环境 |
| `--ready-timeout N` | `180` | 等策略服务就绪的上限（秒） |
| `--keep-tunnel` / `--no-tunnel` | — | 保留隧道 / 完全不动隧道 |

常用客户端参数：

| 参数 | 说明 |
| --- | --- |
| `--task NAME` | 任务名，见 `权重与数据集路径.md` 的 34 任务清单 |
| `--eval-num 1 \| native` | 覆盖每任务 episode 数；`native` 用官方口径 |
| `--only a,b,c` / `--dimension memory` | 批量任务筛选（配合 `--tasks-file`） |
| `--env-gpu 0/1` | 指定仿真用哪张 4090 |

| `--dry-run` | 只打印将执行的命令，不真跑 |


### 3.4 复用到其他机器

1. **服务端**：拉 OpenDM 仓库 → 准备一份 RoboDojo 检出（提供 `XPolicyLab/` + `env_cfg/`）→ 准备权重与 `norm_stats.json` → `setup` → `start`。机器相关路径全部可用参数或环境变量覆盖，脚本内没有硬编码假设。
2. **客户端**：拉 RoboDojo 仓库（确认 `XPolicyLab/policy/OpenDM` 存在，见 7.1）→ 配好到服务端的免密 SSH → `split_policy_client.sh run`。
3. **两端必须一致**：`env_cfg/arx_x5.yml` 与 `action_type=joint`（见 7.3）；`XPolicyLab` 版本需同源（见 7.1）。


### 3.5 并行加速（多进程 / 多环境）

三个独立旋钮，互不干扰：

| 旋钮 | 位置 | 默认 | 作用 |
| --- | --- | --- | --- |
| `--procs K` | 服务端 | 1 | A100 上起 K 个独立策略进程，端口 `7891..7891+K-1`。**只能 K=1**，见下 |
| `--procs-per-gpu P` | 客户端 | 1 | 每张卡起 P 个仿真进程。**上限 P=2** |
| `--envs-per-proc N` | 客户端 | 1 | 每个进程内并行 N 个环境（批推理）。P=2 时 **N=5 最优** |

总并发环境数 = `卡数 × P × N`。

> **结论先给**：2 卡最优 = **`P=2 / N=5`（20 环境）→ 9.25 步/秒**，比默认（`P=1/N=1`，6.87 步/秒）快 **35 %**。下面是能直接抄的命令，完整 12 组配置矩阵见 `评测性能分析与调参指南.md`。

**推荐配置（2 卡 × 每卡 2 进程 × 每进程 5 环境 = 20 个环境）**

```bash
# ① 服务端：起 1 个策略进程（K≥2 会被宿主内存 OOM 杀掉，见下）
bash script/robodojo_policy_server.sh start --procs 1

# ② 客户端：建一条隧道（worker 数多于端口数时脚本会轮转复用）
bash scripts/internal/split_policy_client.sh tunnel-up --policy-port 7891

# ③ 客户端：先激活仿真环境（不激活会被预检拦住），再跑并行 sweep
source /root/miniforge/etc/profile.d/conda.sh && conda activate RoboDojo
bash scripts/internal/smoke_all_tasks.sh --mode client \
  --gpu-ids 0,1 --procs-per-gpu 2 --envs-per-proc 5 \
  --policy-host 127.0.0.1 --policy-port 7891 \
  --policy-name OpenDM --ckpt external \
  --eval-num native --resume --run-id my_run
```

`--policy-port` 数量少于 worker 数时会**轮转复用**（4 个 worker 对 1 个端口 → 全部走 `7891`），sweep 还会按预估负载把任务分给 worker。

**三条会直接浪费你半小时的参数约束**

1. **任务数 ≥ worker 数**（= `卡数 × P`）。不满足时脚本**直接 `exit 2`，一个模拟器都不会启动**，从输出上看很像「配置跑不起来」。用 `--only` 时务必数一下任务数；不写 `--only` 跑全量（54 个）最省心。
2. **`--eval-num` ≥ `--envs-per-proc`**，否则种子数少于环境数，批内对不齐。
3. **`P ≤ 2`**。P=3 会撞满 24 GB 显存（实测 23.5 GB），worker 会在启动阶段或跑到一半分配显存失败，且**失败是竞态的**——重跑一次报废的可能是另外几个任务。

**实测扩展性（P=2、4 个 worker、同一批任务、2 张 4090）**

| N | 环境 | 墙钟 | episodes | 每 episode | 聚合吞吐 | 客户端显存 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 4 | 550 s | 8 | 68.8 s | 7.94 步/s | 16.8 GB |
| 2 | 8 | 520 s | 8 | 65.0 s | 8.40 步/s | 18.2 GB |
| 3 | 12 | 757 s | 12 | 63.1 s | 8.65 步/s | 20.2 GB |
| 4 | 16 | 1023 s | 16 | 63.9 s | 8.54 步/s | 20.2 GB |
| **5** | **20** | 1181 s | 20 | **59.0 s** | **9.25 步/s** ⭐ | 22.3 GB |

⚠️ **五条和直觉相反的结论**（推导与证据见性能文档）：

- **瓶颈在客户端的 Isaac Sim 渲染（占决策周期 79 %），不在服务端推理（仅 15 %）。** 所以「优化推理」几乎没用。
- **服务端显存根本不是约束**：每多一个并发环境只多 **不到 1 GB**（1 环境 22.8 GB → 12 环境 34.1 GB → 20 环境 34.0 GB），80 GB 卡随便用。
- **服务端进程数 `K` 卡在宿主内存，不是显存**：单进程加载权重时宿主内存峰值约 **65 GB**，容器 cgroup 上限 119 GB → **K≥2 必被内核 OOM 杀掉**。
- **N 的拐点取决于 P**：单进程（P=1）时 N=4 就见顶，P=2 时最优点右移到 **N=5**。别照搬别人的 N。
- **堆环境数的收益已经很薄**：N=3 → 5 只快 **6.9 %**，环境数却多了 67 %。想再快得加卡或砍工作量。

## 4. 性能参考（2026-09-28 ~ 09-29 实测）

> 本节只放**单进程单环境**的精确构成（用来理解瓶颈在哪）。**集群/并行配置的完整矩阵与调参见 `评测性能分析与调参指南.md`。**

单环境（`cover_blocks`，546 步）每个决策周期的精确构成 —— 用客户端按调用类型分时探针 + 服务端 `_predict` 探针实测：

| 阶段 | 耗时 | 占比 |
| --- | --- | --- |
| **Isaac Sim 渲染 + 观测处理** | **4.91 s** | **79%** |
| A100 前向（`get_action` 往返） | 1.00 s | 15% |
| 图像上传（`update_obs`×25） | 0.41 s | 6% |
| **周期合计** | **6.32 s** | 100% |

对应吞吐 **3.96 步/秒**（若推理完全免费，上限也只有 4.5 步/秒）。**瓶颈是 Isaac Sim 渲染，不是隧道，也不是 A100 前向。**

| 指标 | 数值 |
| --- | --- |
| 服务端加载耗时 | 首次 ~2 min 10 s；再启动 ~24 s（2 进程并行加载） |
| 单 episode 总耗时 | ~200 s（其中 Isaac Sim 启动 ~57 s） |
| 单 episode 帧数 / 推理次数 | ~546 帧 / **22 次**（546 ÷ 25 ≈ 21.8，吻合） |
| 单次推理耗时 | 中位 **1.09 s**（p95 1.39 s；首次含 CUDA graph 捕获 2.2 s） |
| 服务端显存 | 单进程 22.8 GB；**每多一个并发环境 <1 GB**（12 环境 34.1 GB、20 环境 34.0 GB） |
| 客户端显存 | 单进程 ~8 GB；每多一个进程/环境各 +~0.4 GB（P=2/N=5 时 22.3 GB，已接近 24 GB 上限） |
| 子进程启动耗时 | N=1 57.5 s，N=2 66.8 s，N=4 100.1 s（随环境数增长） |

> ⚠️ 本文档早期版本在这里写过「**每多一个并发环境 +12 GB**」，**那是错的**：它由两个单点读数（1 环境 22.8 GB、2 环境 34.8 GB）线性外推而来，据此会误判「12 环境需要 155 GB 必爆」，而实测 20 个环境也只要 34 GB。
> **教训：显存必须采一整段序列取峰值，不能采单点。** 那个 34.8 GB 是加载期的瞬态峰值，不是稳态。

> ⚠️ 本文档早期版本写的"4.4 步/秒"是按总时长倒推的乐观值，实际纯仿真是 3.96 步/秒，此处已按分阶段实测更正。

## 6. 踩坑记录（报错 → 原因 → 解法）

| 报错 / 现象 | 原因 | 解法 |
| --- | --- | --- |
| `ModuleNotFoundError: No module named 'h5py'`（后续还有 `websockets` / `msgpack` / `msgpack_numpy`） | 共享 conda `opendm` 环境未装 XPolicyLab 的依赖 | 叠加式 venv（`--system-site-packages`）补装，不改共享环境；`setup` 已内置 |
| `FileNotFoundError: .../XPolicyLab/utils/../../env_cfg/arx_x5.yml` | 策略代码假定 XPolicyLab 位于 RoboDojo 仓库内，需要同级 `env_cfg/` | 复制客户端的 `env_cfg` 到策略代码同级；`setup` 已内置 |
| `FileNotFoundError: OpenDM normalization statistics are required: <目录>` | 适配器要求 `norm_stats_path` 指向**文件** | 传 `.../DM05-MEM-Robodojo-Sim/norm_stats.json`（不是目录） |
| `Skipping NVIDIA GPU due CUDA being in a bad state` | `CUDA_VISIBLE_DEVICES` 与 Omniverse 设备枚举不一致的**误报** | 忽略；实测 `torch.cuda.is_available()=True` 且仿真正常用 GPU |
| `ssh host '... nohup ... &'` 命令**不返回**、ssh 一直挂着 | 后台进程继承了 ssh 通道 | 加 `</dev/null` 重定向（脚本内已加） |
| `ssh: Could not resolve hostname a100` | 客户端机器**没有** `Host A100` 别名（别名只在你本机的 ssh config 里） | 在客户端 `~/.ssh/config` 写别名，或用 `--ssh-target root@<ip> --ssh-port <port>` |
| `remote port forwarding failed for listen port 64500` | 服务端 64500 被 10 天前的僵尸会话占着，且本机代理 7897 未运行 | **与本流程无关**（`.bashrc` 已全局 unset 代理） |
| 从客户端 `git submodule update` 卡死、留下 `objects/pack/tmp_pack_*` | 该机器到 `github.com` 的 **HTTPS 大包传输会挂死**（`ls-remote` 这类小交互却正常，极易误判为网络可达） | 改为**从本地共用副本取对象**，见 7.2 |
| `fatal: transport 'file' not allowed` | git 默认禁止 submodule 走 file 协议 | `git -c protocol.file.allow=always submodule update --init XPolicyLab` |
| `error: external filter 'git-lfs filter-process' failed`（`policy/Spirit_v15/.../rc_results.png`） | LFS 对象拉不到，`filter.lfs.required=true` 导致 checkout 整体失败 | `GIT_LFS_SKIP_SMUDGE=1 git checkout --force <commit>` |
| `pkill` 后 ssh 直接返回 255 | `pkill -f` 的模式匹配到了执行命令的 ssh 会话自身 | 用方括号规避：`pkill -f 'setup_policy_serve[r].py'` |
| 客户端 `ss` 看不到 7891 监听 | 该容器 `ss` 读不到监听表（不是没监听） | 用 `/dev/tcp` 或 python socket 验证 |
| 服务端日志停在 `Loading weights` 不动 | Python stdout **块缓冲**，进度不可见 | 以端口监听为判据 |
| `ModuleNotFoundError: No module named 'isaaclab'`（跑 sweep 时） | `smoke_all_tasks.sh` 不会替你激活仿真环境，只有 `split_policy_client.sh run` 会 | 先 `conda activate RoboDojo`；脚本已加预检直接报错（可用 `ROBODOJO_SKIP_ENV_CHECK=1` 跳过） |
| 服务端 `start` 被调用方超时杀掉后，**输出和异常全部消失** | 旧的 `start` 用 `exec` 前台运行，stdout 是调用者的管道，调用者一死就 EPIPE | 已改为 `setsid` 后台 + 每进程独立日志（`/tmp/robodojo_policy_server/server_<port>.log`），`start` 就绪后立即返回 |
| 多客户端并发时担心推理串行 | 服务端有**全局 `_model_lock`**，同一时刻只有一次前向 | 不是问题：单进程能力约 **1.0 次推理/秒**，而 20 环境跑到 9.25 步/秒也只用到 **37 %**（9.25 ÷ 25 步/次 = 0.37 次/秒）。**而且想靠加 `--procs` 扩容也扩不了——K≥2 会被宿主内存 OOM 杀掉** |
| `--envs-per-proc 2` 配 `--eval-num 1` | 种子数少于环境数，批内对不齐 | 用 `--eval-num native`（每任务 25–50）或至少 ≥ `--envs-per-proc` |
| `smoke_all_tasks.sh` **秒退**，日志里连一个 Isaac Sim 都没起（极易误记成「这个配置跑不起来」） | 脚本断言 **任务数 ≥ worker 数**，不满足直接 `exit 2` | 数一下 `--only` 的任务数是否 ≥ `卡数 × --procs-per-gpu`；凑不够就干脆不写 `--only` 跑全量 |
| `--procs-per-gpu 3` 报 Vulkan `ERROR_OUT_OF_DEVICE_MEMORY`、`CUDA error 700` 或 `PhysX failed to allocate GPU memory` | 每卡 3 个 Isaac Sim 进程约 23.5 GB，撞满 24 GB 上限 | **P ≤ 2**。注意 P=3 的失败是**竞态**的：谁先分配到显存谁活，重跑一次报废的可能换成另外几个任务，别指望「多试几次能成」 |
| 中途按瞬时速率估的「还要多久」严重偏大 | 多 worker 争抢 GPU 时单 worker 速率会被压低一个数量级；别的 worker 一退出它立刻恢复满速 | 别在争抢期外推。要估就等竞争结束，或直接等实测墙钟（实测偏差可达 10 倍） |
| 调大 `render_interval`（如 10 → 25）→ 跑批 **64 秒内 4/4 任务全灭**，一集都没跑 | Isaac Sim 硬约束 `渲染频率 % 相机频率 == 0`；相机频率 = `collect_freq` = 25 Hz，而 `render_interval=25` 对应渲染 10 Hz，不整除 → **创建相机时直接抛异常** | **这个参数只能调小不能调大**，合法值仅 **1 / 2 / 5 / 10**。要减少渲染必须连 `collect_freq` 一起降（会改模型输入语义）。调试可用 `ROBODOJO_RENDER_INTERVAL=<N>` 覆盖，详见 `评测性能分析与调参指南.md` |
