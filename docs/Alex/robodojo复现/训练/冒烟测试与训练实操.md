## 2. 冒烟测试怎么设计的

目标只有一个：**验证"官方权重 + 官方数据集 + 官方入口"这条链路能不能跑起来**，不做收敛验证。因此相对官方命令做了 4 处收缩：

| 参数 | 官方 | 冒烟 | 原因 |
| --- | --- | --- | --- |
| `--nproc_per_node` | 8 | **1** | 本机只有 1 卡 |
| `--trainer-config.num-train-steps` | 30000 | **3** | 只要证明能出 loss、能存档 |
| `--trainer-config.per-device-train-batch-size` | 4 | **1** | 显存只剩 45 GB |
| `--trainer-config.save-steps` | 10000 | **1000000** | 不在中途存 12 GB；最后仍会存一次 |

另外：输出目录放 CFS，`WANDB_MODE=offline`（避免联网上报卡住），`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`（压碎片）。

### 2.1 实际执行的命令（LoRA 版，已通过）

## 4. 三个坑 + 显存账本 + flash-attn 安装记录

### 4.1 flash-attn 缺失时：文档那条 sdpa 参数在**训练**路径上无效 ⚠️（2026-09-30 已装上，本节留作排错参考）

`权重与数据集路径.md` 的"已知坑 1"说：RoboDojo 入口默认 `vision_attn_implementation="flash_attention_2"`，**显式加 `--model-config.vision-attn-implementation sdpa` 即可**。

实测在**训练**路径上不成立。报错长这样：

```
File ".../opendm/exp/dm05_exp.py", line 184, in build_model
    model = self._load_base_checkpoint_model()
File ".../opendm/exp/dm05_exp.py", line 112, in _load_base_checkpoint_model
    return DM05ForConditionalGeneration.from_pretrained(...)
File ".../opendm/model/dm05/dm05_arch.py", line 439, in __init__
    self.vlm = Gemma3ForConditionalGeneration(vlm_config_ref)
...
ImportError: FlashAttention2 has been toggled on, but it cannot be used due to the
following error: the package flash_attn seems to be not installed.
```

原因：`DM05-MEM/config.json` 的 `vlm_config.vision_config.attn_implementation = "flash_attention_2"`，**模型构造阶段**就会校验注意力后端；而命令行那个参数只在构造**之后**的 `set_attention_implementation()` 里生效（`dm05_model.set_attention_implementation(...)` → `self.model.vlm.set_attn_implementation(...)`），救不了构造期。

**解法（本机采用，零改动仓库代码）**：造一个"sdpa 视图"目录，真 `config.json` + 其余文件软链到官方权重。仓库里既有的 `DM05-sdpa-verify` 就是这个套路，照抄即可：

```bash
cd /mnt/cfs/opendm/checkpoints
mkdir -p DM05-MEM-sdpa
python3 - <<'PY'
import json, pathlib
src = pathlib.Path('DM05-MEM'); dst = pathlib.Path('DM05-MEM-sdpa')
cfg = json.loads((src / 'config.json').read_text())
v = cfg['vlm_config']
v['attn_implementation']['vision_config'] = 'sdpa'    # 复合映射
v['vision_config']['attn_implementation'] = 'sdpa'    # 子配置自身（构造期真正生效的那个）
(dst / 'config.json').write_text(json.dumps(cfg, indent=2) + "\n")
for f in sorted(src.iterdir()):
    if f.name == 'config.json':
        continue
    link = dst / f.name
    if link.is_symlink() or link.exists():
        link.unlink()
    link.symlink_to(f'../DM05-MEM/{f.name}')
PY

# 校验：应当输出 vision: sdpa | text: flex_attention
/root/miniconda3/envs/opendm/bin/python -c "
from opendm.model.dm05.dm05_arch import DM05Config
c = DM05Config.from_pretrained('/mnt/cfs/opendm/checkpoints/DM05-MEM-sdpa')
print('vision:', c.vlm_config.vision_config._attn_implementation,
      '| text:', c.vlm_config.text_config._attn_implementation)"
```

之后 `--model-config.model-name-or-path` 指向 `DM05-MEM-sdpa`（**权重本身就是官方 `DM05-MEM`，一个字节没变**）。

> **彻底解法已于 2026-09-30 落地**：flash-attn 2.8.3 已在本机编译安装，官方权重 `DM05-MEM` 现在可以原样使用，**不再需要 sdpa 视图**。安装过程与踩坑见 4.5。

### 4.2 `model_max_length` 不能低于 1536 ⚠️

为了省显存把 `--trainer-config.model-max-length` 从 1536 降到 1024，会在前向时报：

```
ValueError: Image features and image tokens do not match, tokens: 654, features: 768
```

因为 3 路相机各 256 个 soft token（共 768）被截断到只剩 654 个。**1536 是这个入口的硬下限**，不要动它。

### 4.3 tyro 的布尔参数语法与 Literal 值域

| 字段类型 | 写法 | 反例 |
| --- | --- | --- |
| `bool`（`liger_kernel: bool = False`） | 裸开关 `--model-config.liger-kernel` | `--model-config.liger-kernel True` → `Unrecognized options: True` |
| `bool \| None`（`use_lora: bool \| None = False`） | 必须带值 `--use-lora True` | `--use-lora` 单独写 → `invalid choice ... Expected one of ('False', 'True', 'None')` |
| `Literal[...]` 值域 | 只能取声明过的值 | `--model-config.llm-attn-implementation flash_attention_2` → `invalid choice ... Expected one of ('auto','eager','sdpa','flex_attention')`（**LLM 不支持 FA2**，见 4.6） |

三种写法错误都以 **exit 2 + 十几行 argparse 风格的框**结束，容易被误读成"程序崩了"、甚至误判成"这个功能用不了"。看到 `Invalid choice` / `Unrecognized options` 先查参数语法和值域。

### 4.4 显存账本：全参 SFT 为什么差一口气

本卡 79.15 GB，另一容器的进程**常驻 34.06 GB**，本容器只有 **45.09 GB**。全参 SFT 连续 6 次都在**优化器 step** 处 OOM（**2026-09-30 卡空出来后，同一套命令一次通过**，见 4.6）：

| 尝试 | 变更 | torch 已分配 | 本进程合计 | 结果 |
| --- | --- | ---: | ---: | --- |
| 1 | 官方配置（torchrun） | 41.69 GB | 45.06 GB | ❌ 差 100 MB |
| 2 | `model-max-length 1024` | — | — | ❌ 先撞 4.2 的截断错误 |
| 3 | `expandable_segments:True` | 41.68 GB | 45.02 GB | ❌ 差 100 MB |
| 4 | 加 Liger kernel | 41.69 GB | 45.06 GB | ❌ 差 100 MB |
| 5 | 绕开 torchrun（`WORLD_SIZE=1` 直接 python）省 NCCL | 42.09 GB | 44.98 GB | ❌ 差 100 MB |
| 6 | 装好 flash-attn、官方权重 + 默认 FA2 | 41.68 GB | 45.02 GB | ❌ 差 100 MB |

根因是**权重 + 梯度 + 优化器状态**这三座大山，Liger 只省激活、`expandable_segments` 只省碎片，都动不了它们：

- 权重 bf16 ≈ 11.7 GB，梯度 bf16 ≈ 11.7 GB；
- Muon 的动量缓冲是 **fp32**（`opendm/optimizer/muon_adamw.py`：`buffer` 由 `grad.detach().float()` 累加），Adam 部分的状态也是 fp32 两套；
- `trainer.py` 的 FSDP 分支（`fsdp1 and world_size > 1`）**没有 CPU offload**，且单进程时根本不启用。

失败点固定在 `_adamw_step → _state_for_param → torch.zeros_like(param, dtype=torch.float32)`，即**第一次给参数分配优化器状态**的瞬间。

**结论**：全参 SFT 需要 **≳50 GB 独占显存**，本卡被占掉 34 GB 时必然失败。这是资源问题，不是代码缺陷——**6 次尝试全部跑完了前向与反向，只是停在优化器 step**。2026-09-30 卡空出来后，同一套命令 **batch 1 / batch 4 双双一次通过**（实测峰值 57.7 / 68.3 GiB，见 4.6）。

### 4.5 flash-attn 安装记录（2026-09-30 完成）

现状：conda 环境 `opendm` 内 `flash_attn 2.8.3`，`is_flash_attention_2_available() == True`。

三个坑（前两个正是 2026-09-21 那次失败的原因）：

1. **架构开关是 `FLASH_ATTN_CUDA_ARCHS`，不是 `TORCH_CUDA_ARCH_LIST`。** `setup.py:70` 只读 `os.getenv("FLASH_ATTN_CUDA_ARCHS", "80;90;100;120")`；脚本里设 `TORCH_CUDA_ARCH_LIST=8.0` **完全无效**，nvcc 命令行照样出现 `-gencode 80/90/100/120` 四套架构——白编 3/4 的活，还把内存打爆。
2. **`MAX_JOBS` 必须压住 cgroup 内存。** 容器 cgroup 上限 119 GiB，16 个并发 nvcc（每个 `--threads 4` × 多架构）直接打满，多个 nvcc 被 OOM killer 杀掉 → `ninja: build stopped: subcommand failed`，日志里表现为一串 `Killed`。本次 `MAX_JOBS=6` + 单架构，内存稳定在 ~100/119 GiB，无一被杀。
3. 前情（2026-09-21 已知）：pip 直连镜像拉 sdist 会卡在 ~35 KB/s；`setup.py` 会先去 GitHub releases 找预编译 wheel 而**永久挂住**。所以要 `curl` 手工拉 sdist + `FLASH_ATTENTION_FORCE_BUILD=TRUE`。

执行（脚本已按上述两点修正：`.smoke/scripts/install_flash_attn.sh`）：

```bash
cd /root/workspace/opendm
unset http_proxy https_proxy HTTP_PROXY HTTPS_PROXY
MAX_JOBS=6 bash .smoke/scripts/install_flash_attn.sh 2>&1 | tee .smoke/logs/install_flash_attn.log
# → [2026-09-30 15:20:44] pip rc=0；Successfully installed flash_attn-2.8.3
```

实测：73/73 编译目标、单架构 `sm_80`、总耗时约 **33 分钟**（14:48 → 15:20），零 OOM。sdist sha256 `1e71dd64…e0370d`（= 镜像 index 登记值）；另备了 `2.8.3.post1`（sha256 `55d5103e…30c348`）作后备，本次未用上。上次失败的日志保留在 `.smoke/logs/install_flash_attn.attempt1.log` 以便对照。

验证三步（全部通过）：

```bash

python -c "

print('fwd/bwd ok', tuple(out.shape), bool(torch.isfinite(q.grad).all()))"
# ② 仓库识别
python -c "from opendm.model.dm05.dm05_utils import is_flash_attention_2_available as f; print(f())"   # → True
# ③ 端到端：官方原始权重 + 默认 FA2 跑 3 步（命令同 2.1，
#    但 --model-config.model-name-or-path 用 DM05-MEM，不带 sdpa 参数）
```

③ 的结果：`vision attn = flash_attention_2`、`text attn = flex_attention`，构造期不再报错，3 步 loss `0.5981 / 1.116 / 0.4819`，checkpoint 落盘，用时 25.1 s（与 sdpa 版 25.45 s 基本持平——batch=1 时瓶颈不在注意力后端）。

> 遗留：`DM05-MEM-sdpa` 视图现在可以删（留着也不影响，做 A/B 对照时还用得上）。**全参 SFT 的显存瓶颈与 flash-attn 无关**（卡在优化器状态，见 4.4）；而且在本工作负载上 **FA2 相对 SDPA 并不提速**，见 4.6。

### 4.6 全参 SFT 实测（2026-09-30 卡空闲）与 FA2 / SDPA 对照

前提：卡完全空闲（`nvidia-smi` 读到 0 MiB）、官方权重 `DM05-MEM` + 默认 FA2，其余同 2.1（3 步、`cover_blocks`、norm_stats 指官方那份）。显存取 **2 s 采样的序列峰值**，不是单点（沿用本仓库自己的测量纪律）。

| 配置 | rc | loss（3 步） | 稳态步时 | 峰值显存 | 存档 |
| --- | --- | --- | --- | ---: | --- |
| **全参 b1** | 0 | 0.5964 / 1.109 / 0.5174 | ~2 s/步 | **59058 MiB（57.7 GiB）** | ✅ |
| **全参 b4** | 0 | 0.6813 / 0.5533 / 0.5386 | ~5 s/步 | **69934 MiB（68.3 GiB）** | ✅ |
| SDPA b1（对照） | 0 | 0.6019 / 1.113 / 0.5454 | ~2 s/步 | 59058 MiB | ✅ |
| SDPA b4（对照） | 0 | 0.6688 / 0.552 / 0.5637 | ~4–5 s/步 | 69936 MiB | —（`save-strategy no`） |

产物核验（全参 b1）：`checkpoint-3/model.safetensors` **11,658,431,136 B**（与官方权重同尺寸），`norm_stats.json` 的 sha256 与官方 `DM05-MEM-Robodojo-Sim/norm_stats.json` **逐字节一致**；`optimizer.pt` **35.2 GB** —— 4.4 里"优化器状态是主要开销"的实物证据；整个输出目录 55 GB。

**结论 1（显存）**：单卡 80 GB 能跑全参。batch 1 占 **57.7 GiB**、batch 4 占 **68.3 GiB**。**b4 只剩约 11 GiB 余量**，同卡再有别的工作负载或序列变长就不安全；单卡建议 **b1 + `gradient-accumulation-steps`**，或 b2 折中。

**结论 2（flash-attn 到底有没有用）**：先厘清一件事——**本入口里 FA2 只作用于 vision tower**（后端值域、内核级对照与"SDPA 默认就在用 flash 内核"的物证，见同目录 `注意力后端说明.md`）。入口的三个后端字段写死了各自的值域：

| 字段 | 允许值 | 默认 | 说明 |
| --- | --- | --- | --- |
| `model-config.llm-attn-implementation` | `auto / eager / sdpa / flex_attention` | `flex_attention` | **没有 `flash_attention_2`**；传了直接 `Invalid choice` 秒退 |
| `model-config.vision-attn-implementation` | `auto / eager / sdpa / flash_attention_2` | `flash_attention_2` | FA2 唯一能落地的地方 |
| `model-config.action-attn-implementation` | `auto / eager / sdpa / flex_attention` | `sdpa` | 同样没有 FA2 |

所以上面四组对照换的是**视觉塔**后端（3 图 × 256 token = 768 token，占比很小）：**FA2 与 SDPA 打平**，步时与峰值显存在噪声内（59058 vs 59058 MiB、69934 vs 69936 MiB）。这与"视觉塔太小、换后端看不出差别"的预期一致。

那"如果 LLM 也能上 FA2 会不会更快"？用内核级微基准按 Gemma3 的文本形状量一下（bf16 + causal + fwd&bwd，A100-80G；torch 2.11 的 SDPA 会派发到 cuDNN/cutlass flash 后端）：

| 形状 (B,H,S,D) | FA2 ms | SDPA ms | SDPA/FA2 |
| --- | ---: | ---: | ---: |
| (1,8,1536,256) Gemma3 文本·单条 | 0.83 | 0.73 | 1.14×（FA2 更慢） |
| (4,8,1536,256) | 2.11 | 2.11 | 1.00× |
| (4,8,5888,256) | 18.25 | 15.52 | 1.18×（FA2 更慢） |
| (4,8,11776,256) | 53.83 | 54.33 | 1.01× |
| (4,8,1536,128) | 1.06 | 1.07 | 1.01× |
| (4,8,4096,128) | 4.40 | 4.51 | 1.02× |
| (4,32,4096,128) | 13.73 | 14.17 | 1.03× |
| (1,8,11776,128) | 6.20 | 6.39 | 1.03× |

即使在 11776 token 的长序列上，FA2 也只有 1–3% 的优势（`head_dim=256` 时反而更慢）。**结论：在这套 A100 + torch 2.11 组合上，装 flash-attn 的收益是"配置与官方默认对齐、不必再造 sdpa 视图"，而不是提速。** 真提速要靠多卡、更大的有效 batch，或削减数据侧开销。

**结论 3（步时量级）**：全参稳态约 **2 s/步（b1）**、**约 5 s/步（b4）**。b4 是 4 倍数据量、只换来 ~2.5 倍步时，说明还有固定开销（图像/视频解码、dataloader 流水）没被打满。

**踩到的一个小坑**：连着起两个 run 会撞 `torchrun` 默认端口 **29500**，第二个 run 秒退，日志里只有一句
`DistNetworkError: ... EADDRINUSE, message: address already in use`，很像"配置错误"。前一个 run 还在写 55 GB 存档时端口不会释放 —— 并发或紧接着重跑请加 `--master_port <另一个端口>`。

## 6. 时间预算（实测与推算分开写）

| 项 | 数值 | 性质 |
| --- | --- | --- |
| 冷启动（进程/CUDA 初始化 + 加载权重 + 建索引 + 首次分配优化器状态） | ≈ 1–1.5 min | 实测 |
| LoRA batch=1 单步 | 首步 8.6 s，稳态 **~2–4 s/步** | 实测 |
| **全参 batch=1 单步** | 首步 ~9.5 s，稳态 **~2 s/步** | 实测（4.6） |
| **全参 batch=4 单步** | 首步 ~43 s，稳态 **~5 s/步** | 实测（4.6） |
| 单卡全参跑 30000 *步*（b1，每步 1 样本） | ≈ **17 h** | **推算**（30000 × 2 s） |
| 单卡凑够官方**数据量**（30000 步 × 全局 batch 32 = 96 万样本） | b1 需 96 万步 ≈ **22 天**；b4 需 24 万步 ≈ **14 天** | **推算**，单卡不现实 |
| 一次存档开销（约 55 GB：12 GB 权重 + 35 GB 优化器 + 8 GB 其他） | ≈ 40 s | 实测 |

> ⚠️ 单卡要出可用模型，**别照搬 30000 步**：先用小步数（如 1000–3000）看 loss 曲线与评测成功率，再决定是否投入多卡。上表"数据量等效"那行说明：官方配方（8 卡 × batch 4 × 30000 步）在单卡上是**周级**投入，不是小时级。
