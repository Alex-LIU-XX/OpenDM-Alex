## 0. 两条命令速查

两台机器各一条命令，隧道与就绪探测都封装在脚本里：

```bash
# ① 服务端（策略所在机器，本环境为 A100）
ssh A100
cd /root/workspace/opendm
bash script/robodojo_policy_server.sh setup     # 仅首次：准备代码 + 隔离 venv
nohup bash script/robodojo_policy_server.sh start </dev/null > /tmp/policy_server.log 2>&1 &
bash script/robodojo_policy_server.sh status    # server/port/gpu/staged 一览

# ② 客户端（仿真所在机器，本环境为 4090）
ssh robodojo
cd /root/workspace/Alex/robodojo
bash scripts/internal/split_policy_client.sh run --task cover_blocks --eval-num 1
```

客户端脚本会自动完成：建 SSH 隧道 → 等策略服务真正应答 → 跑 `robodojo.sh client` → 收尾关隧道。

收尾与排查：

```bash
bash script/robodojo_policy_server.sh stop           # 服务端：停服务、释放显存
bash scripts/internal/split_policy_client.sh status  # 客户端：隧道/服务/策略目录 状态
bash scripts/internal/split_policy_client.sh tunnel-down
```

> **`</dev/null` 不能省**：若后台进程继承了 ssh 通道，`ssh host '... &'` 会**一直挂着不返回**（命令其实已经执行了）。加上 `</dev/null` 即可正常返回。客户端脚本内部启动隧道时也带了 `</dev/null`。

```
└───────────────────────────────┬───────────────────────────────────┘
                                │ ws://127.0.0.1:7891
                                │ ssh -L 7891:localhost:7891 → A100:2537
┌───────────────────────────────▼───────────────────────────────────┐
│                     服务端 / 策略推理 (A100)                        │
│  /root/workspace/Alex/xpl/XPolicyLab   策略代码私有副本（117M）      │
│  /root/workspace/Alex/xpl/env_cfg      动作维度配置                 │
│  /root/workspace/Alex/policy_venv      叠加式 venv（补依赖）        │
│  <opendm>/script/robodojo_policy_server.sh   启动脚本              │
│  权重: /mnt/cfs/opendm/checkpoints/DM05-MEM-Robodojo-Sim (23.32G)  │
│  GPU: 1×A100-80GB（常驻约 23 GB，推理峰值约 35 GB）                 │
└───────────────────────────────────────────────────────────────────┘
```

**为什么必须走隧道**：两台都是容器实例，**只对外映射了 SSH 端口**（A100→2537，4090→5727），任意业务端口从公网不可达（实测 `120.48.62.164:7891` 为 CLOSED）。两台之间 SSH 互通（4090→A100:2537 ✅，A100→4090:5727 ✅），因此在客户端侧建 `ssh -L` 隧道即可。

**协议**：XPolicyLab 自带的 **WebSocket** 策略协议（`protocol: ws`），不是 OpenDM 的 HTTP `/v1/infer`。隧道对 ws 透明，无需额外配置。

## 3. 使用步骤

两个脚本是本链路的入口，隧道、就绪探测、依赖补齐都封装在里面：

| 脚本 | 所在仓库 | 子命令 |
| --- | --- | --- |
| `script/robodojo_policy_server.sh` | OpenDM | `setup` / `start` / `status` / `stop` |
| `scripts/internal/split_policy_client.sh` | RoboDojo | `run` / `tunnel-up` / `tunnel-down` / `status` |

### 3.1 服务端准备与启动

```bash
ssh A100
cd /root/workspace/opendm

bash script/robodojo_policy_server.sh setup    # 仅首次；幂等，可重复执行
nohup bash script/robodojo_policy_server.sh start </dev/null > /tmp/policy_server.log 2>&1 &
bash script/robodojo_policy_server.sh status
```

`setup` 做四件事（全部幂等）：

1. 从 RoboDojo 检出复制 `XPolicyLab`（**排除 `policy/Pi_05`**，它单独占 9.4 G）到 `$WORKDIR/xpl`；
2. 复制 `env_cfg`（策略适配器靠它推导动作维度，必须与客户端一致）；
3. 建**叠加式 venv** 并补装 `h5py / websockets / msgpack / msgpack-numpy` —— **不触碰共享 conda 环境**；
4. 校验关键文件与 import。

启动行为要点：

- **首次启动约 2–3 分钟**（从 CFS 读 23 GB 权重），**后续约 20–40 秒**（页缓存命中）
- ⚠️ 日志会**块缓冲**，`Loading weights` 停住不代表卡死；**以端口监听为就绪判据**
- 客户端脚本会自己等就绪，通常**不需要手动等待**

`setup` 参数：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--robodojo-repo PATH` | `/root/workspace/RoboDojo` | 提供 `XPolicyLab/` 与 `env_cfg/` 的 RoboDojo 检出 |
| `--workdir PATH` | `/root/workspace/Alex` | 代码与 venv 的落盘位置 |
| `--force` | — | 即使已暂存也重新复制代码 |

`start` 参数（均可用环境变量覆盖）：

| 参数 | 环境变量 | 默认 |
| --- | --- | --- |
| `--ckpt PATH` | `ROBODOJO_CKPT` | `/mnt/cfs/opendm/checkpoints/DM05-MEM-Robodojo-Sim` |
| `--port N` | `ROBODOJO_PORT` | `7891` |
| `--task NAME` | `ROBODOJO_TASK` | `cover_blocks` |
| `--bind-host HOST` | `ROBODOJO_BIND_HOST` | `127.0.0.1`（走隧道时保持回环） |
| `--gpu ID` | `ROBODOJO_GPU` | `0` |

### 3.2 客户端跑推理

```bash
ssh robodojo
cd /root/workspace/Alex/robodojo
bash scripts/internal/split_policy_client.sh run --task cover_blocks --eval-num 1
```

`run` 依次做：**建隧道（含连通性前置检查）→ 等策略服务真正应答 → 跑 `robodojo.sh client` → 关隧道**。

`split_policy_client.sh` 参数（`--` 之后的参数**透传**给 `robodojo.sh client`）：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--ssh-target HOST` | `A100` | SSH 别名，或直接写 `user@host` |
| `--ssh-port N` | 取自 ssh config | SSH 端口 |
| `--ssh-key PATH` | `~/.ssh/id_ed25519` | 免密私钥 |
| `--policy-port N` | `7891` | 要桥接的远端端口 |
| `--policy-dir PATH` | `XPolicyLab/policy/OpenDM` | 仓库相对路径 |
| `--conda-env NAME` | `RoboDojo` | 仿真环境 |
| `--ready-timeout N` | `180` | 等策略服务就绪的上限（秒） |
| `--keep-tunnel` / `--no-tunnel` | — | 保留隧道 / 完全不动隧道 |

常用客户端参数：

| 参数 | 说明 |
| --- | --- |
| `--task NAME` | 任务名，见 `权重与数据集路径.md` 的 34 任务清单 |
| `--eval-num 1 \| native` | 覆盖每任务 episode 数；`native` 用官方口径 |
| `--only a,b,c` / `--dimension memory` | 批量任务筛选（配合 `--tasks-file`） |
| `--env-gpu 0/1` | 指定仿真用哪张 4090 |
| `--seed 0` | layout 种子 |
| `--dry-run` | 只打印将执行的命令，不真跑 |

换任务并指定 GPU 与种子：

```bash
bash scripts/internal/split_policy_client.sh run --task stack_bowls -- --env-gpu 1 --seed 3
```

> **客户端需要能免密 SSH 到服务端**：脚本会先做一次连通性检查，失败时给出明确提示。本环境已在 4090 的 `~/.ssh/config` 写入 `Host A100`；换机器时自己配别名，或直接 `--ssh-target root@<ip> --ssh-port <port>`。

结果落在**客户端仓库**：

```
eval_result/RoboDojo/<task>/OpenDM/arx_x5/0_ckpt_name=external,action_type=joint/<时间戳>/
├── _result.json                              # success_rate / score / details
├── episode_0000000_cam_head_success.mp4      # 三路相机成功视频（640×480@25fps）
├── episode_0000000_cam_left_wrist_success.mp4
└── episode_0000000_cam_right_wrist_success.mp4
```

### 3.3 状态查询与停止

```bash
# 服务端
bash script/robodojo_policy_server.sh status   # server / port / gpu / staged
bash script/robodojo_policy_server.sh stop     # 停服务并释放显存

# 客户端
bash scripts/internal/split_policy_client.sh status   # 隧道 / 服务应答 / 策略目录

```

### 3.4 复用到其他机器

1. **服务端**：拉 OpenDM 仓库 → 准备一份 RoboDojo 检出（提供 `XPolicyLab/` + `env_cfg/`）→ 准备权重与 `norm_stats.json` → `setup` → `start`。机器相关路径全部可用参数或环境变量覆盖，脚本内没有硬编码假设。
2. **客户端**：拉 RoboDojo 仓库（确认 `XPolicyLab/policy/OpenDM` 存在，见 7.1）→ 配好到服务端的免密 SSH → `split_policy_client.sh run`。
3. **两端必须一致**：`env_cfg/arx_x5.yml` 与 `action_type=joint`（见 7.3）；`XPolicyLab` 版本需同源（见 7.1）。

## 6. 踩坑记录（报错 → 原因 → 解法）

| 报错 / 现象 | 原因 | 解法 |
| --- | --- | --- |
| `ModuleNotFoundError: No module named 'h5py'`（后续还有 `websockets` / `msgpack` / `msgpack_numpy`） | 共享 conda `opendm` 环境未装 XPolicyLab 的依赖 | 叠加式 venv（`--system-site-packages`）补装，不改共享环境；`setup` 已内置 |
| `FileNotFoundError: .../XPolicyLab/utils/../../env_cfg/arx_x5.yml` | 策略代码假定 XPolicyLab 位于 RoboDojo 仓库内，需要同级 `env_cfg/` | 复制客户端的 `env_cfg` 到策略代码同级；`setup` 已内置 |
| `FileNotFoundError: OpenDM normalization statistics are required: <目录>` | 适配器要求 `norm_stats_path` 指向**文件** | 传 `.../DM05-MEM-Robodojo-Sim/norm_stats.json`（不是目录） |
| `Skipping NVIDIA GPU due CUDA being in a bad state` | `CUDA_VISIBLE_DEVICES` 与 Omniverse 设备枚举不一致的**误报** | 忽略；实测 `torch.cuda.is_available()=True` 且仿真正常用 GPU |
| `ssh host '... nohup ... &'` 命令**不返回**、ssh 一直挂着 | 后台进程继承了 ssh 通道 | 加 `</dev/null` 重定向（脚本内已加） |
| `ssh: Could not resolve hostname a100` | 客户端机器**没有** `Host A100` 别名（别名只在你本机的 ssh config 里） | 在客户端 `~/.ssh/config` 写别名，或用 `--ssh-target root@<ip> --ssh-port <port>` |
| `remote port forwarding failed for listen port 64500` | 服务端 64500 被 10 天前的僵尸会话占着，且本机代理 7897 未运行 | **与本流程无关**（`.bashrc` 已全局 unset 代理） |
| 从客户端 `git submodule update` 卡死、留下 `objects/pack/tmp_pack_*` | 该机器到 `github.com` 的 **HTTPS 大包传输会挂死**（`ls-remote` 这类小交互却正常，极易误判为网络可达） | 改为**从本地共用副本取对象**，见 7.2 |
| `fatal: transport 'file' not allowed` | git 默认禁止 submodule 走 file 协议 | `git -c protocol.file.allow=always submodule update --init XPolicyLab` |
| `error: external filter 'git-lfs filter-process' failed`（`policy/Spirit_v15/.../rc_results.png`） | LFS 对象拉不到，`filter.lfs.required=true` 导致 checkout 整体失败 | `GIT_LFS_SKIP_SMUDGE=1 git checkout --force <commit>` |
| `pkill` 后 ssh 直接返回 255 | `pkill -f` 的模式匹配到了执行命令的 ssh 会话自身 | 用方括号规避：`pkill -f 'setup_policy_serve[r].py'` |
| 客户端 `ss` 看不到 7891 监听 | 该容器 `ss` 读不到监听表（不是没监听） | 用 `/dev/tcp` 或 python socket 验证 |
| 服务端日志停在 `Loading weights` 不动 | Python stdout **块缓冲**，进度不可见 | 以端口监听为判据 |

### 7.4 换权重 / 换任务

- **换任务**：客户端 `--task <name>` 即可，**服务端不必重启**（服务端 `task_name` 只用于日志/记录）。
- **换权重**：`bash script/robodojo_policy_server.sh start --ckpt <新路径>`（需同为 DM0.5 RoboDojo 契约；换基座权重前先核对 `norm_stats.json` 与动作空间）。
